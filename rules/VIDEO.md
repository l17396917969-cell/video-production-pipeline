# 视频制作规则库

这份是**内容与画面的判断标准**，来自实际做片时踩出来的经验，以及用户明确提过的要求。
和 `DESIGN.md`（视觉规范）、`MISTAKES.md`（技术错误清单）并列，三者不重复。

每次开新片子前读一遍，交付前对照自查。

---

## 一、选题角度：讲"我用了"，不讲"它是什么"

这是最容易犯、也最致命的错。

**市面上已经太多的两种视频：**
- 介绍项目"是什么"——功能列表、截图、五个亮点
- 介绍"怎么用"——点这里、点那里

**稀缺的、也是唯一值得做的：**

> 站在**真实使用**的视角，讲**怎么用、有什么坑、瓶颈在哪**。

所以脚本必须有这三样，缺一样就是产品介绍：

1. **一个我自己踩过的坑**（不是引用别人的总结，是我真撞上的）
2. **一个瓶颈判断**（不是"它很快"，而是"快到这里就卡住了"）
3. **一句能被人引用的结论**（不是"值得一试"，而是有立场的判断）

### 反例（我做过的）
> "它不做模型也不做 Agent，只做一件事：管住别人家的 Agent。六万三千星。"

这是介绍。观众看完知道它是什么，但不知道自己该不该用。

### 正例（重写后的）
> "我花了两小时把 T3 Code 装上，先给结论：它解决的不是写代码的问题。"

一开口就是体验，观众立刻知道这条片子在讲"我的判断"，不是"官方介绍"。

## 二、脚本结构

**开头 3 句内必须给判断**，不要铺垫背景。

推荐的骨架：

| 位置 | 写什么 | 例子 |
| --- | --- | --- |
| 第 1 句 | 我的成本 + 结论 | 我花了两小时装上，先给结论 |
| 第 2–4 句 | 它到底解决什么问题 | 它不是编辑器，是调度台 |
| 中段 | 我自己跑通的证据 | 我丢给它一个任务，它自己读文件 |
| 中段 | **坑**，一个接一个 | 坑一 / 坑二 / 坑三 |
| 结尾 | 瓶颈在哪 + 一句判断 | 瓶颈从写代码变成审查 |

**坑要给编号**（坑一、坑二、坑三），观众才记得住，也方便剪成切片。

**每个坑必须能对上画面证据**：真实截图、真实命令输出、真实报错。空口说坑没人信。

## 三、画面规则

### 3.1 实机画面占比

**硬要求：实机操作画面（真实录屏）不少于全片的 25%，单一实机镜头不超过 5 秒。**

T3 Code 那条片子就是反面教材：实机只有 2 个镜头，剩下全是截图推拉，看起来像"看图说话"。

### 3.2 必须覆盖"从头跑通"的过程

一个项目视频，**至少要有一段完整的过程**：
- 怎么装
- 怎么启动
- 怎么跑出第一个结果

缺了这段，观众会觉得"你只是截了图，没真的用过"。

### 3.3 素材类型至少三种

只有一种素材 = 电子相册。合格的组合：

| 类型 | 作用 | 例子 |
| --- | --- | --- |
| 真实截图 | 证明"它长这样" | GitHub 页、官网、产品界面 |
| 真实录屏 | 证明"它真的会动" | 终端、浏览器、App 操作 |
| 数据可视化 | 证明"它有多重" | 真实数字的图表、3D 柱 |
| 结构图 | 解释"它在哪一层" | 3D 架构爆炸图 |
| 真实输出 | 证明"它真跑出了东西" | 命令回显、报错、返回结果 |

**禁止**：全片只有"截图 + 推拉变焦"。

### 3.4 讲 GitHub 项目，开场不要截仓库页

这是调研出来的结论，也是我自己踩过的坑。

**仓库页是最差的第一个镜头**：信息密度太高（文件列表、分支、issue、语言条），观众第一眼只会看到"一堆看不懂的东西"，看不出这项目值不值得看。

成熟的开源项目宣传片是这么排的（五拍，约 13 秒）：

| 拍 | 画面 | 要点 |
| --- | --- | --- |
| 1 | `owner/repo` 大字 | 逐字升起，别一行直接怼出来 |
| 2 | star 数从 0 滚到值 | **数字是故事脊柱**，峰值处一道光扫过 |
| 3 | 贡献者头像墙 | 波浪式入场，要有"人来了"的感觉，不是"格子填满" |
| 4 | 终端逐字打出安装命令 | 2–3 行封顶，一墙 npm 输出叫堆料 |
| 5 | Star it on GitHub | 一行就够 |

**但纯黑底叠数字也是 PPT。** 唯一的解法是拿真实画面打底：把录屏压暗到 35–40%，上面再压数字和名字。字要压得住，画面要还看得见。

这也是为什么素材必须先录够——没素材的时候，任何"高级排版"都是拿黑底糊弄。

三条硬规矩：

- **一个强调色，只用在三处**：数字峰值、终端绿勾、CTA 按钮。其他地方全中性。
- **背景永远是低透明度纹理**，不许跟内容抢。
- **数字必须是滚动的**，静态数字没有节奏。

对应组件：`T116RepoIntro`（第 1、2 拍合一）。

### 3.5 3D 用在哪

3D 不是装饰，只在两种情况下用：
- **数据有纵向含义**（柱子高度 = 数量压力）
- **结构有层级含义**（层的上下 = 谁调用谁）

平铺信息用 3D 只会让字更难认。

## 四、节奏

| 指标 | 标准 |
| --- | --- |
| 镜头数 | 每 10 秒 ≥ 3 个（60 秒片 → 18 个以上） |
| 单镜时长 | 2–6 秒，没有一镜超过 8 秒 |
| 同一张图的连续机位 | 不超过 2 个 |
| 静止画面 | 不允许（必须有运镜或内容变化） |

**加快节奏的办法不是剪短，是切机位**：一张图拆全景/局部/推近，素材没变，镜头数翻倍。

---

## 五、技术红线

1. **不编数据**。数字必须能从截图、文档、命令输出里对上。编一个数字，整条片子就废了。
2. **不编体验**。"我用了两周"这种话，没真用就别写。
3. **坑必须是真坑**。自己没撞上的，宁可不写。
4. **实机画面里的报错不要藏**，但也不要让它占据主要位置——它是真实的一部分。

## 六、交付前自查

做完一条片子，按顺序问自己：

1. 第一句话是判断还是背景？（背景 = 重写）
2. 有没有三个具体的坑？坑有画面证据吗？
3. 实机录屏超过 25% 了吗？有完整跑通的过程吗？
4. 素材有几种类型？只有截图吗？
5. 镜头数够吗？平均时长超过 5 秒吗？
6. 有没有一句能被人单独引用的结论？
7. 有没有一个数字是我编的？（有 = 删掉或找回证据）
